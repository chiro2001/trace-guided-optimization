# 2026-10-29 实测记录

以下 ARM 结果来自 920B-47。正数为候选减少比例 `1 - candidate / baseline`，报告逐对
比例的中位数和范围，不合并不同批次。训练画像、原生计时和验证分别执行。

| 负载 / 画像 | 验证 | ROI 时间减少中位数 | 逐对范围 | 结论 |
| --- | --- | ---: | ---: | --- |
| 32 个 4KiB 对齐热函数 / QEMU，自建 BOLT | 独立 5 对 | 57.93% | 56.53%～62.16% | 选择布局 |
| 新构建 CPython 3.12.13 前端 microbench / QEMU | 独立 5 对 | 11.71% | 8.87%～17.44% | 选择布局 |
| 同一原生合成负载 / SPE 兼容桥 | 3 对直接验证 | 58.31% | 56.05%～58.46% | 候选通过 |
| vLLM CPU-stub decode / cycles IP 样本，仅 libpython | 3 对 | -3.93% | -5.17%～-2.81% | 保留原版 |
| vLLM CPU-stub decode / SPE，仅 libpython | 3 对 | -3.47% | -5.36%～-1.81% | 保留原版 |
| vLLM CPU-stub decode / retired SPE，三库 recovery | 独立 5 对 | 3.68% | 2.50%～6.41% | 候选通过 |

原生合成负载有意把 32 个热函数放在 4KiB 边界，制造取指压力，不能作为现实程序
收益的替代。Python microbench 包含实际解释器方法调用、属性、字典和整数控制流。
其基线为本项目构建、保留重定位的 Python；不代表任意发行版 Python 都有同等收益。
两个 QEMU 训练例均使用较短训练循环，再绑定同分布的较长验证循环。

确认阶段的 PMU 同样记录在 JSON。原生合成负载的 cycles 减少约 57.95%，前端停顿
减少约 74.74%，L1I read miss 减少约 99.99%，指令数基本不变；Python 对应约为
11.72%、88.24%、96.56%，指令数减少约 0.46%。只在 enabled/running 相同的记录上
解释未复用计数，原始值保留，不把 QEMU 时间或 SPE latency 当作原生性能。

SPE 转换测试的 36,103 条分支样本全部读到了对应指令字，没有未知编码或代码缺失。
转换不会向附近分支移动 PC。预测位在本路径不可用，因此不声称得到完整误预测计数。

单文件分发测试 `appimage-e2e-r1` 使用 AppImage 完成 QEMU 采集、三种布局搜索和
独立确认，生成 `build/appimage-venv/bin/python3.tgo`。AppImage 退出后，直接执行该
ELF 仍可使用优化 DSO；`sys.prefix` 保留原虚拟环境。该轮 ROI 中位数减少约 58.04%。

最终 alpha 的额外分发测试移除了 PATH 中的编译器和系统 Python，在较短的两百万
次循环上完成独立确认，ROI 中位数减少约 54.11%；项目外执行新入口时，ROI helper
来自 bundle，而不是临时 AppImage 挂载目录。

vLLM 使用固定镜像的 CPU-stub/Qwen3.5-0.8B，纯 eager、无 cudagraph；每次目标区间
是四次 engine.step 加各自同步，预热和 prefill 在外。两种单候选均保持 token JSON
一致并实际加载了优化 libpython，但性能回退。结果不外推为真实 NPU 吞吐或数值精度。
随后对 SPE 画像搜索 ext-tsp、compact、aligned 三种布局，初筛中位数分别为
-1.99%、-0.76%、-0.78%，最终自动保留原版，未将其中任何一项发布为获益候选。

新一轮使用 `arm_spe_0/ts_enable=1,branch_filter=1,event_filter=0x2,jitter=1/u`，
只在 decode ROI 采样。自动构建的 recovery BOLT 同时优化 libpython、
libtorch_npu 和 libtorch_python；显式允许 stripped ELF，只处理有画像的函数，
没有启用 assume-code-pages-safe。原文件未覆盖。先做三对筛选，再做独立五对确认，
五对 ROI 时间减少分别为 5.71%、2.50%、6.41%、3.68%、3.61%。全部 token JSON
一致，三库实际映射与 SHA256 均验证通过。对应入口在
`runs/vllm-spe-retired-multi-r1/run`，供相同容器环境使用。

确认阶段主线程用户态 PMU：先对每个进程的请求 ROI 取中位数，再计算五对变化。
cycles 中位数减少 4.03%，frontend stall cycles 减少 10.85%；instructions 增加
1.22%，L1I read miss 事件增加 8.01%。全部计数 enabled=running、无 open errors。
因此不能把该结果描述为所有缓存指标改善；这仍只是 CPU-stub 主机 decode 路径，
不外推为真实 NPU 吞吐或数值精度。原始五对和派生计算见
`evidence/2026-10-29/vllm-retired-multi-r1-{confirmation,summary}.json`。

Go 最初的本地 perf 发现约 137K 样本，compiler 占约 77.6%。随后实现原生 toolexec
CPU profile、PGO 重建与 Go linker 包内布局，均通过实际 compiler 替换和语义
fixture。下表为冷 GOCACHE、`-p 1`、完整 `cmd/compile` 构建 wall time，预热两对
不计入结果。它不是 decode ROI，也不能直接解释为前端 PMU 改善。

本地布局实际移动 10,625 个符号，1,279 个唯一 profile 函数匹配最终 ELF 顺序，
没有地址逆序。它证明变换执行了，不能证明性能收益。ARM SDK 与本地发行版 SDK
构建设置不同，结果不混合比较。ARM 包内布局测量期间，同机另有不重叠 CPU 集合
上的 LLVM 构建，结果仅用于筛选，尚无 ARM Go 获益声明。

runtime 布局的 r1 发现了覆盖范围问题：整包排除特殊 text 类型，导致 compiler
负载的 runtime 实际被跳过；该轮不作为 runtime 性能结论。修复后的 ARM r2 已
在最终 ELF 中核对 207 个 runtime 画像函数，实际移动 1,357 个 runtime 符号，
没有地址逆序。完整冷缓存编译筛选中，ARM 三对均回退；本地三对中有一对回退，
未进入独立确认。两侧均自动
保留原版，没有将局部正收益标为 Go 优化成功。

各轮小型原始 JSON 见 [evidence/2026-10-29](../evidence/2026-10-29)。目标仍保持 active。

## 0.3.0 自动策略验证

复用 `vllm-spe-retired-r1` 画像，未指定 image、BOLT mode 或 allow-stripped，工具
自动选择 libpython、libtorch_npu、libtorch_python 并逐库启用 recovery。该轮仅搜索
ext-tsp 布局，三对初筛中位数 3.13%；独立五对为 4.00%、7.56%、5.54%、2.92%、
4.74%，中位数 **4.74%**。token 一致，三库真实加载。对应主线程 cycles 减少 4.89%，
frontend stall cycles 减少 10.43%；instructions 增加 0.96%，L1I read miss 增加
9.27%。全部 PMU enabled=running、无 open errors，不能称为所有缓存指标改善。

另一轮用 AppImage 从头采集，自动探测到 retired SPE，同样选择三库。整组 ext-tsp
初筛中位数 -1.51%，随后探测六个真子集，并对两个有希望的子集完整初筛，仍未达标，
最终 baseline。两份训练画像来自不同 CPU 亲和性下的独立采集，验证两臂各自保持相同
配置；结果不合并，也不把旧画像的获益当作新画像必然有效。这表明仍需提高画像稳定性。

原生前端合成负载通过 AppImage 自动选择 SPE，默认比较三种布局，独立五对 ROI
减少中位数 56.55%（56.17%～57.90%）；cycles 减少 56.62%，frontend stall cycles
减少 73.06%，L1I read miss 减少 99.96%，指令数基本不变。独立 ROI 脚本未导入源码
目录，基线与候选均使用 bundle 提供的 helper。新容器在项目只读、PATH/PYTHONPATH
清空、cwd=/tmp 的情况下执行最终入口，通过校验及优化库映射验证。

跨容器部署实测发现旧 stat 检查会把同内容 overlay 文件误判为漂移。TGOCFG02
入口新增原生 SHA256 回退，保留元数据快速路径；本地和 ARM 各 22 项测试通过。
升级后的最终包另做 compact 布局原生确认，中位数 56.85%（56.01%～58.71%）。
已确认 vLLM 三库保持字节不变，用新格式重新生成相邻入口后，在新容器的
`/usr/local/python3.12.13/bin/python3.tgo` 实际运行，token 和三库映射均通过。
最终发布包再做独立五对 compact 复核，ROI 减少中位数 57.38%（56.43%～58.71%）。
包 SHA256 为 `a766757f7f31c38358355c068da7eaf762825c71c860ba0e947f273a9d0bed98`，
也通过无 C 编译器的 Go capture/layout/项目外入口 smoke。该 smoke 不作为 Go 收益证据。

上述证据见 [auto-0.3.0](../evidence/2026-10-29/auto-0.3.0/)。vLLM 仍仅表示 CPU-stub
eager 主机 decode 路径，所有百分比为时间/事件减少比例。
